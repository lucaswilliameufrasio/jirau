# Plan — Native scaffold CLI (Rust + Android + iOS)

Nov 7, 2026 · Lucas Eufrasio

> **Status as of November 9, 2026 (template 0.4.0).** This is the original plan, kept as a historical record. Since then:
>
> - All phases have been completed. Besides the five planned commands, there are `run` (builds, installs and launches on a device/simulator, watch mode by default), `test` (core, ffi, Android instrumented, XCTest on the simulator, desktop), `add` and `upgrade`.
> - `upgrade` performs a real 3-way merge using `.jirau/template-base/` as the base; projects without a base get `<file>.jirau-new` side files for review.
> - The Rust core is really linked on both platforms via UniFFI library mode, through `scripts/build-ios-ffi.sh` and `scripts/build-android-ffi.sh` (the latter is invoked by Gradle in `preBuild`).
> - Pinned versions no longer have `libs.versions.toml` and `Cargo.toml` as their source of truth: they now live in `src/templates/versions.rs` and are checked against the official registries by `scripts/check-template-versions.sh`. The versions mentioned in "Fast builds" (Gradle 8.14, etc.) are satchel's versions at the time.
> - Android uses Gradle only. Amper was supported for a while and then removed (its Gradle plugin mode was discontinued and standalone Amper has no stable 1.0).
> - There is desktop support (Rune UI), SQLite (`rusqlite`), a `vault` template with encryption, and an English/Portuguese CLI (`--lang`).
>
> See the [README](../README.md) for the current state.

## Goal and philosophy

A Rust CLI that generates and operates projects with satchel's structure: a Rust core, an Android app in Kotlin with Compose and an iOS app in Swift with SwiftUI. The goal is the `flutter create` + `flutter doctor` + `flutter run` experience without giving up native UI.

What sets it apart from Crux, mobiler and jffi:

- **The core holds only logic.** It does not own the UI nor impose a message-and-effects architecture.
- **The UI is native and framework-free.** On Android: Navigation Compose, `ViewModel` + `StateFlow` and direct calls into the core. On iOS: `NavigationStack` and `@Observable`. It is the same principle as Flutter with native routing and a provider.
- **The bridge is pure UniFFI.** No hand-written JNI and no custom layer between UniFFI and the app.
- **The generated project does not depend on the CLI.** After `new`, it builds with just `cargo`, Gradle and Xcode. The CLI is a shortcut, not a runtime.

The CLI comes first and a TUI later, only if it is missed. A `doctor` with colored output covers most of the case.

The template is extracted from satchel, which already has `crates/`, `android/` and `TESTING_STANDARD.md`. The first project generated by it is the curupira app.

## Name: jirau

The CLI is called **jirau**, and the generated project's configuration file is `jirau.toml`.

In the riverside houses of the Amazon, a jirau is a raised wooden platform built to hold things. In practice, it is a scaffold. That describes what the tool does: it builds the structure the app rests on and gets out of the way, because the generated project does not depend on it.

The name follows the same line as curupira, tucupi, acari and sabiá, with regional terms tied to the project's purpose. It is also short and easy to type: `jirau new`, `jirau doctor`, `jirau dev`.

The other options considered were tipiti (the basket that shapes cassava and from which tucupi comes), maloca (the communal house, several apps under a single core) and puxirum (the community work party). Jirau won because it is the only one that means a supporting structure.

## Generated structure

`new` generates a Cargo workspace at the root, with the native apps as sibling folders. It is the same shape as satchel, but with `-ffi` in UniFFI and iOS already included.

```text
my-app/
├── Cargo.toml               # workspace
├── crates/
│   ├── my-app-core/         # pure logic, no FFI, tested with cargo test
│   └── my-app-ffi/          # UniFFI: exports the core to Kotlin and Swift
├── android/
│   ├── settings.gradle.kts
│   ├── gradle.properties    # caches already enabled (see Fast builds)
│   ├── gradle/libs.versions.toml
│   └── app/                 # Compose, Navigation, ViewModel
├── ios/
│   ├── project.yml          # XcodeGen; the .xcodeproj is not versioned
│   └── App/                 # SwiftUI, NavigationStack, @Observable
├── TESTING_STANDARD.md
└── jirau.toml               # name, bundle id, dev ABIs, template version
```

Template decisions:

- **Separate `core` and `ffi`.** The `core` does not know about UniFFI. Tests run fast on the host, and the FFI only adapts types.
- **Generated bindings stay out of Git.** Kotlin goes to `android/app/build/generated/uniffi` and Swift to `ios/Generated/`. Both are regenerated by `bindings`.
- **Native libraries.** On Android, one `.so` per ABI in `jniLibs/`. On iOS, an `XCFramework` with device and simulator.
- **XcodeGen instead of Tuist.** It is a single YAML file, with no Swift DSL. It avoids `.pbxproj` conflicts and lets iOS be generated on Linux, even though building still requires a Mac.
- **Centralized versions** in Android's `libs.versions.toml` and in the workspace `Cargo.toml`.

## Commands

There are five commands, each equivalent to a step of the Flutter flow.

| Command | What it does | Flutter equivalent |
| --- | --- | --- |
| `new <name>` | Generates the project from the template, with name, package, bundle id and platforms (`--android`, `--ios`). | `flutter create` |
| `doctor` | Checks rustup and the targets (`aarch64-linux-android`, `x86_64-linux-android`, `aarch64-apple-ios`, `aarch64-apple-ios-sim`), NDK, `cargo-ndk`, JDK, Android SDK, emulator, Xcode, XcodeGen and simulators. Shows the command that fixes each missing item. | `flutter doctor` |
| `dev [android\|ios]` | Watches `crates/`, recompiles the core only for the active device's ABI, regenerates the bindings and reinstalls. The UI is left to the IDE's previews and Live Edit. | `flutter run` |
| `bindings` | Regenerates Kotlin and Swift from `-ffi`. | `build_runner` (just the good part) |
| `build [android\|ios] --release` | Produces the AAB/APK with the three ABIs and the XCFramework with device and simulator. | `flutter build` |

Details:

- **`dev` finds the ABI on its own.** It uses `adb shell getprop ro.product.cpu.abi` on Android and the chosen simulator or device on iOS.
- **`doctor` has `--json`** for use in CI.
- **Later:** `upgrade`, which applies a new template version with a three-way merge, as mobiler does. The template version is stored in the configuration file.

## Fast builds

The template ships configured for the short loop. The biggest win in Gradle is the configuration cache. In Rust, it is compiling a single ABI in dev.

**Gradle.** The generated `gradle.properties`:

```properties
org.gradle.jvmargs=-Xmx4g -XX:+UseParallelGC -Dfile.encoding=UTF-8
org.gradle.caching=true
org.gradle.configuration-cache=true
org.gradle.parallel=true
kotlin.daemon.jvmargs=-Xmx2g
android.useAndroidX=true
android.nonTransitiveRClass=true
```

- Current versions of Gradle, AGP, Kotlin (K2) and the Compose BOM, pinned in `libs.versions.toml`. Satchel is on Gradle 8.14, BOM `2024.10` and coroutines `1.9`, and they are worth updating together.
- KSP instead of kapt, if code generation is ever needed.
- In dev, incremental `installDebug`, never `clean build`. In Studio, Apply Changes and the Compose previews.
- `doctor --profile` runs `./gradlew assembleDebug --profile` and shows where the time went.

**Rust.**

- **One ABI in dev:** `x86_64` on the emulator and `arm64-v8a` on the phone. All three ABIs only in `build --release`.
- **The Gradle task that calls `cargo-ndk` declares inputs and outputs.** The inputs are `crates/**` and `Cargo.lock`; the output is `jniLibs/`. That way it stays up-to-date when the Rust code has not changed and goes into the build cache.
- **`dev` profile with optimized dependencies.** With `[profile.dev.package."*"] opt-level = 2`, dependencies are compiled once and optimized, while your own crate stays fast to compile.
- **`sccache`**, if installed: `doctor` suggests it and `dev` uses it.
- **A single `target/` in the workspace**, shared between Android, iOS and the host tests.

## Phases

Each phase ends with something usable. Phase 1 already improves satchel before any CLI exists.

1. **Extract the template from satchel.**
   - Switch `satchel-ffi` from `jni` to UniFFI and validate it on the `satchel_api35` emulator, with `NativeCatalogTest` passing.
   - Apply the `gradle.properties` and the task with inputs and outputs from the previous section. Measure before and after with `--profile`.
   - Create `ios/project.yml` (XcodeGen) with a minimal SwiftUI app calling the core.
   - Copy the structure into a template directory with placeholders for name, package and bundle id.
2. **`new` and `doctor`.** Run `new` in an empty directory and reach a green `cargo test` + `./gradlew installDebug`, without editing anything by hand.
3. **`bindings` and `dev` for Android.** The watcher, ABI detection and reinstall. The goal is under 10 s between saving a `.rs` file and the reopened app, with a warm cache.
4. **`dev` and `build` for iOS.** Mac only: XCFramework, `xcodebuild` and `simctl`. On Linux, `doctor` explains what is missing.
5. **Generate the curupira app with the CLI.** This is the real test. Anything that needs manual adjustment becomes a template issue.
6. **`build --release` and `upgrade`.** The three ABIs, signing and the template's three-way merge.

`TESTING_STANDARD.md` applies to the CLI itself: `cargo fmt --check`, `clippy -D warnings` and an integration test that runs `new` + `cargo test` in a temporary directory.

## Risks and open decisions

- **iOS depends on the Mac.** Satchel already has its iOS app stuck at "Open on the Mac". Phases 1 and 4 require time reserved on the machine with Xcode.
- **UniFFI changes.** The proc-macro API changes between versions. Pin the version in the template and update it only through `upgrade`.
- **iOS extensions** (File Provider and WidgetKit) need their own targets in `project.yml` and an App Group. The template should include a commented example, because satchel and curupira need it.
- **Competition with jffi**, which has the same goal. It is worth reading its code before phase 2 and deciding whether to contribute instead of starting from scratch.
